# 06-1 PNG Huffman 编码详解

把 **Huffman 编码**（Huffman Coding，霍夫曼编码）理解成一句话：

> **出现频率高的符号用短码，出现频率低的符号用长码，从而降低平均编码长度。**

它是 PNG 里的 DEFLATE 压缩非常核心的一环。在 PNG → zlib → DEFLATE 的链路中，Huffman 负责把 **LZ77 产生的符号进一步编码成 bitstream**。

---

## 1. 先看最简单的例子

假设一段数据只有 4 种符号：

| 符号 | 出现次数 | 概率 |
|---|---:|---:|
| A | 50 | 50% |
| B | 25 | 25% |
| C | 15 | 15% |
| D | 10 | 10% |

如果固定长度编码，因为有 4 个符号，每个符号都需要 2 bit：

```text
A = 00
B = 01
C = 10
D = 11
```

100 个符号总共：

```text
100 × 2 = 200 bit
```

但 A 出现了一半，却仍然每次都要花 2 bit。

Huffman 的思路就是：

```text
A 很常见 → 给短码
D 很少见 → 可以给长码
```

例如可能得到：

```text
A = 0
B = 10
C = 110
D = 111
```

那么平均长度：

```text
A: 50 × 1 = 50
B: 25 × 2 = 50
C: 15 × 3 = 45
D: 10 × 3 = 30
----------------
总计 = 175 bit
```

从固定编码的：

```text
200 bit
```

下降到：

```text
175 bit
```

这就是 Huffman 压缩的本质。

---

## 2. Huffman 编码树怎么构造？

Huffman 的关键不是“随便给高频符号短码”，而是有一个确定的建树算法。

还是：

```text
A = 50
B = 25
C = 15
D = 10
```

首先把权重从小到大排列：

```text
D 10
C 15
B 25
A 50
```

### 第一步：合并最小的两个

```text
D 10 + C 15 = 25
```

变成：

```text
25 (D+C)
25 B
50 A
```

### 第二步：再合并最小的两个

```text
25 + 25 = 50
```

得到：

```text
50 ((D+C)+B)
50 A
```

### 第三步：合并

```text
50 + 50 = 100
```

最终得到一棵树：

```text
                    100
                   /   \
                 A50    50
                       /  \
                     B25   25
                          /  \
                        C15  D10
```

假定：

```text
左分支 = 0
右分支 = 1
```

那么：

```text
A = 0
B = 10
C = 110
D = 111
```

这就是 Huffman code。

---

## 3. 为什么解码时不会歧义？

这是 Huffman 非常重要的一个性质：

> Huffman code 是一种 **Prefix Code，前缀码**。

也就是说：

**任何一个完整码字，都不会是另一个码字的前缀。**

例如：

```text
A = 0
B = 10
C = 110
D = 111
```

不会存在：

```text
B = 10
另一个符号 = 101
```

因为如果 `10` 已经代表 B，那么读到：

```text
10
```

解码器就已经确定是 B。

例如收到 bitstream：

```text
0101101110
```

从左向右走 Huffman tree：

```text
0   → A
10  → B
110 → C
111 → D
0   → A
```

所以：

```text
0101101110
↓
A B C D A
```

不需要分隔符。

---

## 4. 从树的角度理解解码

Huffman 解码器可以把每个 bit 看成一次树遍历：

```text
bit = 0 → 左走
bit = 1 → 右走
```

例如：

```text
                 root
                /    \
              A       *
                    /   \
                   B     *
                        / \
                       C   D
```

输入：

```text
110
```

过程：

```text
root
 ↓ 1
 *
 ↓ 1
 *
 ↓ 0
 C
```

到达叶子节点：

```text
symbol = C
```

然后回到 root，继续解析下一个 symbol。

所以最朴素的 Huffman decoder 可以写成：

```text
node = root

while not leaf(node):
    bit = read_bit()
    if bit == 0:
        node = node.left
    else:
        node = node.right

output(node.symbol)
```

不过实际软件和硬件通常不会真的一 bit 一 bit 地走树，因为性能太低。

---

## 5. Huffman 真正优化的是什么？

Huffman 不是直接让：

```text
压缩后长度 = 最小
```

而是在给定符号概率情况下，构造一个非常好的 **整数 bit 长度前缀码**。

理想的信息量是：

$$
I(x)=-\log_2 P(x)
$$

例如某符号概率：

```text
P = 1/2
```

理想编码长度：

$$
-\log_2(1/2)=1\text{ bit}
$$

如果：

```text
P = 1/4
```

则：

$$
-\log_2(1/4)=2\text{ bit}
$$

如果：

```text
P = 1/8
```

则：

$$
-\log_2(1/8)=3\text{ bit}
$$

因此理想情况：

```text
概率高
↓
-log2(P) 小
↓
编码短
```

这就是信息论背景。

---

## 6. Huffman 编码的是“符号”，不是原始 bit

这点和 PNG / DEFLATE 非常相关。

很多人第一次理解 DEFLATE 时会想成：

```text
原始字节
↓
Huffman
↓
bitstream
```

其实 DEFLATE 更接近：

```text
原始数据
    │
    ▼
LZ77
    │
    ├── Literal
    └── <Length, Distance>
              │
              ▼
           Huffman
              │
              ▼
          bitstream
```

例如原始字符串：

```text
ABCABCABCABC
```

LZ77 可能表示成：

```text
A
B
C
<length=9, distance=3>
```

然后 Huffman 并不是直接编码：

```text
ABCABCABCABC
```

而是编码：

```text
Literal A
Literal B
Literal C
Length symbol
Distance symbol
```

所以二者分工不同：

```text
LZ77
解决：重复字符串

Huffman
解决：符号出现概率不均匀
```

这两个组合起来，就是 DEFLATE 的核心。

---

## 7. DEFLATE 为什么有两套 Huffman Tree？

这点对理解 PNG 很重要。

DEFLATE 中主要有：

### Literal/Length Huffman Tree

编码：

```text
Literal 0~255
End-of-block = 256
Length codes = 257~285
```

也就是：

```text
0 ───────────255
│ literal bytes
│
256
│ End Of Block
│
257──────────285
  Length codes
```

另外还有：

### Distance Huffman Tree

专门编码：

```text
Distance
```

所以一个 LZ77 match：

```text
<Length, Distance>
```

最终变成：

```text
Length symbol
    ↓
Literal/Length Huffman

Distance symbol
    ↓
Distance Huffman
```

然后有些 Length / Distance 还需要追加：

```text
extra bits
```

例如：

```text
Length Symbol
+ Length Extra Bits

Distance Symbol
+ Distance Extra Bits
```

因此一个 match 的 DEFLATE 表达大致是：

```text
┌────────────────────────┐
│ Literal/Length Huffman │
│      Length code       │
└───────────┬────────────┘
            │
       Extra bits
            │
            ▼
┌────────────────────────┐
│   Distance Huffman     │
│    Distance code       │
└───────────┬────────────┘
            │
       Extra bits
```

---

## 8. Fixed Huffman 和 Dynamic Huffman

这也是 DEFLATE 里最关键的区别。

DEFLATE block 有三种主要形式：

```text
BTYPE = 00
Stored / Uncompressed

BTYPE = 01
Fixed Huffman

BTYPE = 10
Dynamic Huffman
```

### 8.1 Fixed Huffman

编码长度由 RFC 1951 直接规定。

例如 Literal/Length：

```text
0–143     → 8 bits
144–255   → 9 bits
256–279   → 7 bits
280–287   → 8 bits
```

也就是说：

```text
不需要发送 Huffman tree
```

Decoder 天生就知道。

优点：

```text
简单
没有 tree header overhead
```

缺点：

```text
不能适应当前数据概率
```

### 8.2 Dynamic Huffman

Dynamic Huffman 则是：

```text
Encoder 分析当前 block 的 symbol frequency
                ↓
             建 Huffman tree
                ↓
             得到 code lengths
                ↓
   把 code lengths 写进 bitstream
                ↓
Decoder 重建 Huffman table
```

所以 Dynamic Huffman 本身还有一部分 overhead。

只有当：

```text
节省的数据 bits
>
描述 Huffman tree 的 bits
```

才划算。

---

## 9. 一个特别重要的概念：实际传输的是 Code Length

DEFLATE 的 Dynamic Huffman 并不会真的发送：

```text
A = 010
B = 11101
C = ...
```

它主要发送的是：

```text
每个 symbol 的 code length
```

例如：

```text
symbol A length = 1
symbol B length = 2
symbol C length = 3
symbol D length = 3
```

然后 Decoder 根据这些长度重新构造 Huffman codes。

为什么可以这样？

因为 DEFLATE 使用：

> **Canonical Huffman Code，规范 Huffman 编码**

这是理解 DEFLATE decoder 非常关键的一步。

---

## 10. Canonical Huffman 是什么？

假设只知道：

```text
A length = 1
B length = 2
C length = 3
D length = 3
```

Canonical Huffman 有确定的规则，可以唯一构造：

```text
A = 0
B = 10
C = 110
D = 111
```

所以不需要把整棵树发送过去。

只需要发送：

```text
code lengths
```

Decoder 就可以重建完全相同的 code table。

这对 DEFLATE 非常重要：

```text
普通 Huffman：
发送 tree 可能很复杂

Canonical Huffman：
只发送 length
↓
decoder 自动恢复 code
```

因此更准确地说，DEFLATE 的 Dynamic Huffman 过程是：

```text
Frequency
   │
   ▼
Huffman tree
   │
   ▼
Code lengths
   │
   ▼
Canonical Huffman
   │
   ▼
Actual codes
```

Decoder：

```text
Code lengths
   │
   ▼
Canonical Huffman reconstruction
   │
   ▼
Decode table
```

---

## 11. 为什么 DEFLATE 还要“再用一个 Huffman”编码 Huffman tree？

Dynamic Huffman 有一个非常巧妙的设计。

需要描述：

```text
Literal/Length code lengths
+
Distance code lengths
```

但如果直接把大量 length 写进去，仍然很浪费。

于是 DEFLATE 又做了一层：

```text
Literal/Length lengths
        +
Distance lengths
        │
        ▼
Run-Length Encoding
        │
        ▼
Code-Length Alphabet
        │
        ▼
再用 Huffman 编码
```

也就是说，有 **Huffman 编码 Huffman 的描述信息**。

DEFLATE 里的 code-length alphabet 是：

```text
0~15 → actual code length

16 → repeat previous length 3~6 times
17 → repeat zero 3~10 times
18 → repeat zero 11~138 times
```

然后这些：

```text
0~18
```

本身又建立一棵：

```text
Code Length Huffman Tree
```

所以 Dynamic DEFLATE 实际上存在 **三类 Huffman 表**：

```text
                    Dynamic DEFLATE

         ┌──────────────────────────┐
         │ Code-Length Huffman Tree │
         │ 描述下面两棵树            │
         └────────────┬─────────────┘
                      │
             ┌────────┴────────┐
             ▼                 ▼
┌──────────────────────┐ ┌──────────────────┐
│ Literal/Length Tree  │ │ Distance Tree    │
│ literal + length     │ │ distance         │
└──────────────────────┘ └──────────────────┘
```

这是 RFC 1951 解码最容易第一次看懵的地方。

## 12. 从 PNG Decoder 的角度串起来

PNG 解码时：

```text
PNG File
   │
   ▼
IDAT chunks
   │
   ▼
concatenate IDAT data
   │
   ▼
zlib stream
   │
   ▼
DEFLATE blocks
   │
   ├── Stored
   ├── Fixed Huffman
   └── Dynamic Huffman
           │
           ▼
       Huffman decode
           │
           ▼
 Literal / Length / Distance
           │
           ▼
        LZ77 copy
           │
           ▼
    Filtered Scanlines
           │
           ▼
     PNG Unfilter
           │
           ▼
         Pixels
```

所以在 PNG 里，Huffman 并不是 PNG 独有算法。

它属于：

```text
PNG
 └── zlib
      └── DEFLATE
           └── Huffman coding
```

对应标准关系是：

```text
PNG        → PNG Specification / ISO/IEC 15948
zlib       → RFC 1950
DEFLATE    → RFC 1951
Huffman    → DEFLATE 内部编码机制
```

## 13. 最需要建立的一个直觉

可以把 DEFLATE 理解成两级压缩：

```text
                 原始数据
                    │
                    ▼
              ┌──────────┐
              │   LZ77   │
              └────┬─────┘
                   │
       把重复数据变成引用
                   │
        ┌──────────┴───────────┐
        │                      │
     Literal             Length/Distance
        │                      │
        └──────────┬───────────┘
                   ▼
              ┌──────────┐
              │ Huffman  │
              └────┬─────┘
                   │
        高频符号用较少 bit
                   │
                   ▼
               bitstream
```

所以：

> **LZ77 消除“空间上的重复”，Huffman 消除“符号概率上的冗余”。**

这句话基本抓住了 DEFLATE 的核心。

---

## 14. 工程化定义总结

**Huffman 编码：**

> 根据符号出现概率构造一棵二叉前缀码树，使高频符号拥有较短码字、低频符号拥有较长码字，从而降低平均编码长度；DEFLATE 使用 canonical Huffman code，并分别编码 Literal/Length 与 Distance symbols。

对于 DEFLATE Decoder，下一步最关键的是理解：

**Canonical Huffman 如何只根据 code length 计算出实际 Huffman code。**

这是从“理解 Huffman”进入“真正能写 DEFLATE decoder”的关键一步。
